# GSTE V0.4 — レポートの読み方

まず最終譜と最上位の人による確認レポートを確認してください。レポートは観察結果を記録するもので、編曲を再決定するものではありません。

## 完全性チェックゲート

| ゲート | 確認する内容 | 意味しないこと |
|---|---|---|
| G1 原曲 | 解析と原曲識別の構造 | 音楽的意味を完全かつ正確に理解していること |
| G2 音楽 | 優先イベントと旋律候補イベントの保持 | 音楽品質や人が確認した完全な旋律 |
| G3 書き出し | 最終イベント列のシリアライズ、欠落、幽霊イベント | 原曲伴奏の全保持や実際の演奏可能性 |
| G4 再生 | XML 再読み込み時の音高、時間、弦、フレットの整合性 | 楽譜ソフト上の表示や音声を実際に検証したこと |

G3 は書き出しの完全性を検査します。運指は `04_FINAL_FINGERING_REVIEW` などの物理的診断で別途確認してください。G4 の「再生」という名称は MuseScore で試聴済みであることを意味しません。

## 読む順序

1. `GSTE_TAB` を読み、変換譜の音楽性と演奏可能性を確認します。
2. `CONVERSION_REPORT.md` または `ERROR_REPORT.md` を読み、状態と直接的な根拠を確認します。
3. `HUMAN_REVIEW_REPORT.md` と `MEASURE_LOCATION_GUIDE.md` で確認が必要な位置を特定します。
4. 詳細な診断が必要な場合は、`debug/00_GSTE_INTEGRITY_GATE.json` と `UNIFIED_RUNTIME_MONITOR.json` の個別結果を確認します。ファイルは `debug/pipeline_output/` にある場合もあります。
5. 原曲伴奏分析、編曲候補、Joint による選択、最終チェック、最終 TAB を比較し、素材が最初に削除・変更された箇所を探します。

`pattern_type` や三連符ラベルは局所的な認識を示すもので、グループ全体の保持を保証しません。原曲音符、候補、選択イベント、最終音符はそれぞれ異なる集団であり、各段階の件数を保持率の分母として混同してはいけません。原曲識別、発音開始、選択オクターブ、最終的に実際に鳴る音を比較してください。

検査に合格しても、旋律、伴奏リズム、和声、接続、持続音、休符、運指、譜面を確認してください。不具合報告では、まず共有が許可されたプライバシー確認済みの簡易概要を提出できます。音楽品質の問題では、権利上共有可能な最小限の楽譜抜粋が必要になる場合があります。

## 一般的な編曲と開発者向けデバッグの違い

通常の編曲では、楽譜の再生、原曲音声トラックとの比較、GAR 運指索引を優先してください。`EVENT_LIFECYCLE_TRACE`、`GSTE_NOTATION_MAP`、`GSTE_EDITOR_CONTEXT` などの診断・対応データは主に開発と問題調査のためのもので、一般ユーザーが全項目を読む必要はありません。バグ報告には、必要に応じてプライバシーを確認した最小限の再現データを提供してください。

## 候補の失敗位置と根本原因

全体移調やオクターブ探索で棄却された位置が、唯一の真のエラー小節とは限りません。候補によって異なる位置で失敗する場合があります。まず原譜の小節ラベルと選択範囲の通し番号を照合し、音域と運指の制約を手動で確認してください。レポートの PASS は音楽性の検証を意味しません。
